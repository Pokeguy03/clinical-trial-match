## 📄 Root-Level Files

### `openenv.yaml` — Environment Identity Card

**Purpose**: Tells the OpenEnv framework "I exist and here's my name."

```yaml
env_name: clinical_trial_match
version: "0.1.0"
description: "Clinical trial patient matching environment"
env_class: server.environment:ClinicalTrialMatchEnvironment
client_class: client:ClinicalTrialEnv
```

| Field | What it does |
|-------|-------------|
| `env_name` | Unique identifier for our environment |
| `version` | Semantic version number |
| `env_class` | Points to the Python class that IS the environment |
| `client_class` | Points to the client class that connects to the server |

**When is it used?** Every time you run `openenv validate` or `openenv push`, it reads this file first.

---

### `pyproject.toml` — Build Configuration

**Purpose**: Defines project metadata, dependencies, and how to install the package.

**Key sections**:
- `[project]` — Name, version, Python requirement
- `[project.dependencies]` — Libraries we need:
  - `openenv-core` — The framework we build on
  - `fastapi` — Web server framework
  - `pydantic` — Data validation
  - `uvicorn` — ASGI server to run FastAPI
  - `fastmcp` — Tool registration framework
- `[build-system]` — Uses `hatchling` to build the package

**When is it used?** When you run `pip install -e .` or `uv sync`

---

### `uv.lock` — Dependency Lock File

**Purpose**: Freezes the exact versions of ALL dependencies (including sub-dependencies). Ensures everyone gets identical packages.

**You never edit this file manually.** It's generated by running `uv lock`.

**Why it exists**: Without it, `pip install` might install different versions on different machines, causing "works on my machine" bugs. The lockfile guarantees reproducibility.

---

### `__init__.py` — Package Entry Point

**Purpose**: Makes the folder a Python package and exports the client class.

```python
from client import ClinicalTrialEnv

__all__ = ["ClinicalTrialEnv"]
```

**What it does**: When someone writes `from clinical_trial_match import ClinicalTrialEnv`, Python finds this file and returns the client class.

### `client.py` — Environment Client

**Purpose**: The class that OTHER programs use to connect to our server and call tools.

```python
class ClinicalTrialEnv(MCPToolClient):
    """Thin wrapper for the Clinical Trial Match environment."""
    pass
```

**How it works**:
1. Inherits from `MCPToolClient` (provided by OpenEnv)
2. Connects to the server via WebSocket
3. Provides methods like `reset()`, `call_tool()`, `list_tools()`
4. Handles serialization/deserialization of messages

**Who uses it**: The `inference.py` script creates a `ClinicalTrialEnv` to interact with our server.

### `models.py` — Action/Observation Types

**Purpose**: Defines the data types for actions (what the AI sends) and observations (what it receives back).

```python
from openenv.core.env_server.mcp_types import (
    CallToolAction,        # "Call this tool with these arguments"
    CallToolObservation,   # "Here's the tool result + reward"
    ListToolsAction,       # "What tools are available?"
    ListToolsObservation,  # "Here are the available tools"
)
```

**Why it exists**: The OpenEnv framework needs this file to know what message formats our environment uses. Required for `openenv push`.

### `inference.py` — The AI Agent (Baseline Script)

**Purpose**: Runs an AI model against our environment and logs results. This is the "player" that tries to solve our "game."

**Size**: ~400 lines | **This is the most complex file in the project.**

**What it does step by step**:

```
1. Read config from environment variables (API_BASE_URL, MODEL_NAME, HF_TOKEN)
2. Connect to our running server via WebSocket
3. For each task (easy, medium, hard):
   a. Reset the environment with env.reset(task="easy")
   b. Send instructions to the LLM
   c. LLM responds with tool calls (e.g., "call list_patients()")
   d. Execute the tool on our server
   e. Send the result back to the LLM
   f. LLM makes next decision
   g. Repeat until all matches submitted or step limit reached
   h. Log final score
4. Print summary of all task scores
```

**Key components**:

| Component | Lines | What it does |
|-----------|-------|-------------|
| `SYSTEM_PROMPT` | 83-105 | Instructions for the AI model |
| `build_tool_definitions()` | 108-198 | OpenAI function-calling schema for our 6 tools |
| `get_model_response()` | 201-219 | Sends messages to LLM, gets response |
| `run_task()` | 222-365 | Main loop: reset → call tools → submit matches → score |
| `log_start/step/end()` | 44-76 | Structured `[START]`/`[STEP]`/`[END]` logging |

### `.dockerignore` — Docker Build Exclusions

**Purpose**: Tells Docker which files to SKIP when building the image.

```
__pycache__
*.pyc
.git
.env
*.egg-info
outputs/
```

**Why it matters**: Without this, Docker would copy cached files, git history, and secrets into the container — making it larger and potentially insecure.

### `server/app.py` — FastAPI Web Server

**Purpose**: Creates the web server that exposes our environment over HTTP/WebSocket.

```python
from openenv.core.env_server.http_server import create_app

app = create_app(
    ClinicalTrialMatchEnvironment,   # Our environment class
    CallToolAction,                   # Action type
    CallToolObservation,              # Observation type
```

**What `create_app()` gives us automatically**:

- Handles `reset`, `step`, `list_tools`, `call_tool` messages

### `server/environment.py` — The Brain (Core Logic)

**Purpose**: This is the HEART of the project. It defines the 6 MCP tools, manages state, and computes rewards.

**Size**: ~320 lines | **Most important file in the project.**

**Class**: `ClinicalTrialMatchEnvironment` inherits from `MCPEnvironment`

#### The 6 Tools (registered via `@mcp.tool` decorator):

| Tool | What it does internally |
|------|----------------------|
| `list_patients()` | Returns summaries from `PATIENTS` dict for current task's patient IDs |
| `get_patient_record(pid)` | Returns full record, marks patient as "reviewed" for bonus points |
| `list_trials()` | Returns summaries from `TRIALS` dict for current task's trial IDs |
| `get_trial_details(tid)` | Returns full protocol, marks trial as "reviewed" for bonus points |
| `submit_match(pid, tid, eligible, reasoning)` | Compares decision against ground truth, calculates reward |
| `get_progress()` | Returns score, matches remaining, review status |

#### Reward Computation (`_compute_match_reward()`):

```python
reward = 0.0

# 1. Was the decision correct?
if eligible == ground_truth["eligible"]:
    reward += 1.0          # +1.0 for correct answer

# 2. Did the reasoning mention key criteria?
for key_reason in ground_truth["key_reasons"]:
    if key_reason mentioned in reasoning:
        reward += 0.25 * (matches / total_reasons)

# 3. Did the AI actually review the data first?
if patient_id in patients_reviewed:
    reward += 0.10         # +0.10 for reading the record
if trial_id in trials_reviewed:
    reward += 0.05         # +0.05 for reading the protocol
```

#### State Management:

| State Variable | Purpose |
|---------------|---------|
| `_task_name` | Current difficulty level (easy/medium/hard) |
| `_patient_ids` | Which patients are in this task |
| `_trial_ids` | Which trials are in this task |
| `_submitted_matches` | Track what's been submitted (prevent duplicates) |
| `_expected_pairs` | All patient×trial pairs that need decisions |
| `_cumulative_reward` | Running total of rewards earned |
| `_patients_reviewed` | Which patients the AI actually looked at |
| `_trials_reviewed` | Which trials the AI actually looked at |
| `_done` | Whether the episode is complete |

#### Key Methods:

| Method | What it does |
|--------|-------------|
| `reset(task="easy")` | Loads task config, clears state, returns instructions |
| `step(action)` | Processes an MCP action, increments step count, checks limits |
| `_compute_match_reward()` | Calculates points for a single decision |
| `_get_max_possible_reward()` | Returns theoretical maximum score |

### `server/Dockerfile` — Container Blueprint

**Purpose**: Instructions for Docker to build a container image.

**Build stages**:

```
Stage 1: BUILDER
├── Start from openenv-base image (has Python 3.11)
├── Copy our source code
├── Install uv + git
├── Run uv sync (install all dependencies)
└── Create .venv with everything installed

Stage 2: RUNTIME (final image)
├── Start from openenv-base image (clean)
├── Copy .venv from builder (just the installed packages)
├── Copy our source code
├── Set PATH and PYTHONPATH
├── Add health check (pings /health every 30s)
└── CMD: start uvicorn on port 8000
```

**Why 2 stages?**: The builder stage installs build tools (git, compilers). The runtime stage only has what's needed to RUN, making the final image smaller and more secure.
